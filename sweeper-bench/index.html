Can agents discover bugs in interactive software?

Paper Code Data

TL;DR SWEeper-Bench is 200 real bugs from 200 open-source web apps. Each task gives an agent the app, a browser, and a request like find and fix issues in board sharing, but no bug report. The best of 15 frontier agents fixes 59% of the bugs, while agents given a description of the bug fix about 96%.

Who finds the bugs?

More and more, we ask AI for software rather than answers: a sign-up form for an event, a booking page, a small tool for the team. The app is ready in minutes and goes straight to the people who will use it.

That makes it interactive software with real end users, and people use software in ways no one planned for. Grandma opens it on an old iPad with the text turned way up, a cousin opens it from Tokyo, two friends press send at the same moment. Each runs into a different bug, and each bug only shows up through their own sequence of taps.

Today, users are how these bugs get found. They report them, the report makes its way back to whoever built the app, and everyone waits for a fix. It happens to the biggest products too:

As more of the software people use is generated on the fly, often for a handful of users and with no testing team in between, this loop matters more. The agent that built the app should use it the way people will, find what is broken, and fix it before anyone else sees it.

Coding benchmarks don’t measure this yet. SWE-bench and its successors start from a bug report someone has already written, so they test diagnosis and repair. SWEeper-Bench starts before anyone has reported anything.

The best agent fixes 59%

Each task gives the agent the app’s code, the running app with a browser, and one sentence such as Find and fix issues in Focalboard’s board sharing and membership. We ran 15 frontier agents, each a model in its native harness. Grok 4.6 in Cursor did best at 59.0%, and nine of the fifteen fixed fewer than half of the bugs. Similar scores also hide very different bills, with cost per task varying more than 30×.

How it works

Each of the 200 tasks comes from a real bug fix merged into a different open-source web app. We roll the app back to just before the fix, so the bug is still there, and it only shows up when someone uses the app in the right way. The agent never sees the bug report, the fix, or our tests.

To grade a fix, a separate verifier agent uses the repaired app in a browser and follows step-by-step behavior tests. One checks that the bug is gone, the other that nearby features still work. The verifier only judges what a user would see, so any fix that works passes.

How reliable is the verifier?

We ran both behavior tests on every buggy version and every reference fix, with three verifier setups, three times each. A perfect verifier fails the target test on the buggy version and passes everything else. All three setups come within one point of that, varying by at most 0.8 points between runs. We use the cheapest, GPT-5.6 Luna in Codex.

Test case: a shared team board doesn’t show up

Focalboard is an open-source project board. Sharing a board with a teammate should put it in their sidebar, but in the buggy version it never appears. Nothing looks wrong to the person sharing, so you only notice if you share the board, log in as the teammate, and look. Here is our verifier doing exactly that.

    127.0.0.1:13200 · Focalboard

    The fix is a single function call. Spotting the bug is the hard part: all four agents whose runs we read reached the empty sidebar, but only two treated it as a bug. Claude Opus 5 checked the unit tests, saw that they expect no sidebar update, and decided the behavior was intended.

    Where agents fall short

    We split each run into stages. About a quarter of the time, the agent never reaches the feature where the bug lives. Another quarter of the time it gets there but never triggers the bug, or sees it and doesn’t recognize it. Once an agent does see the bug, diagnosing and fixing it rarely fail. Finding a bug takes both: looking in the right place, and noticing what is wrong there.

    Fixing really is the easy part. When we replace the open-ended request with a description of the bug, every agent we tried passes about 96% of the tasks.

    More time doesn’t fix it

    Agents that work longer don’t score higher. Grok 4.6 averages 12 minutes per task, while Qwen 3.8 Flash takes 102 minutes for a slightly lower score. Giving the same agent a bigger budget helps up to about 40 minutes, then levels off.

    Looking ahead

    As AI builds more of the software people use, there often won’t be a testing team between the agent and the user. The agent has to use what it built the way someone else would, and notice when something is off, even when the existing tests pass. SWEeper-Bench measures that skill, and because its verifier only checks what a user can see, the same setup could also reward it in training.
