SWEeper-Bench

Can agents discover bugs in interactive software?

Yang Yao1*Haozhe Chen1*Bingyi KangKarthik R Narasimhan1Zhuang Liu1

1Princeton University  ·  *Equal contribution

Paper Code Data Leaderboard

TL;DR

  • Coding agents can build an app in minutes. The bugs in it are still found by the people who use it.
  • SWEeper-Bench gives an agent a real web app, a browser, and one request: Find and fix issues in <some part of the app>. There is no bug report. 200 tasks, each a real bug from a different open-source app.
  • The best of 15 agents, Grok 4.6, passes 59.0%. Told what the bug is, agents pass about 96%. What they lack is noticing the bug, not fixing it.

The two-minute version. Sound on.

01 · the problem

Users are still the testers

Even the biggest software teams ship bugs that users find first. Here is one from late September:

This Glitch Can FULLY CRASH the new iPhone 18 Pro

New iOS glitch has been discovered which can make the iPhone completely UNRESPONSIVE and mess up the entire UI. Apple NEEDS to take action immediately and push a HOTFIX update ASAP.

This is not a minor visual bug. Your iPhone pic.x.com/pFYqcnbnt9

— TechDroider (@techdroider) September 27, 2026

That one got past a company with entire teams of testers. More and more software now gets built with no testers at all. You ask a coding agent for a small app, it builds one in minutes, and you send it out.

Then real people use it, each in their own way. Grandma is on an old iPad with the text turned way up. A cousin is in Tokyo. Two friends press Send at the same moment. Someone on a train taps twice. Each of them runs into something different.

The complaints come back to you, you pass them on to the agent, and everyone waits for a fix. The users have become the test suite.

What if the agent went looking first? You would hand over the app with one line, find and fix issues in the RSVP page, and it would use the thing itself: clicking, breaking, fixing, again and again, before anyone else sees it.

Most coding benchmarks start one step too late. SWE-bench and its successors hand the agent an issue that someone has already written, so they measure diagnosis and repair but not discovery. SWEeper-Bench starts before anyone has reported anything.

We ran 15 frontier agents, each a model paired with its native harness (or Codex if it has none), with up to 8 hours per task. Grok 4.6 in Cursor comes first at 59.0%, which surprised us. Qwen 3.8 Flash follows at 57.5%, and three agents tie at 56.5%. Nine of the fifteen pass fewer than half of the tasks.

Two more things stand out. The failures are misses, not breakage: preservation tests pass 97.5–100% of the time, so agents rarely break what already works. They just don’t find what’s broken. And similar scores hide very different bills. Claude Opus 5 matches Claude Fable 5.1 at twice the cost, and Grok 4.6 averages 12 minutes per task where Qwen 3.8 Flash takes 102. Every number is in the full table.

03 · the benchmark

Software engineering, with a broom

Each task is a real bug that was fixed in a merged pull request of an open-source web app. We roll the app back to the commit before the fix. Every task comes from a different app: 200 apps across seven domains, with a median of 4.6k GitHub stars. We picked bugs that are hard to find but obvious once seen. Any user would agree the behavior is wrong, but it only shows up if you click through the app in just the right way.

What the agent gets

  • the app’s source code
  • the app, running, and reflecting its edits
  • a Chromium browser with Playwright, and a shell
  • one sentence naming a product area:
  • the issue or the pull request
  • the reference fix or the repo history
  • our behavior tests
  • the internet

The entire task descriptionFind and fix issues in Focalboard’s board sharing and membership.

That is all. The agent has to work out how the app is used, guess what might go wrong, and design tests that expose it, the way you would if a colleague asked you to sweep a feature before release.

Graded the way a user would grade it

When the agent stops, we apply its code changes to a fresh copy of the app. A verifier agent then uses the app through the browser, without seeing any code, and follows two behavior tests written as step-by-step instructions. The target test reproduces the bug and checks that it’s gone. The preservation test checks that nearby features still work. A task passes only if both pass, so any fix that works for the user counts, however it is written.

How reliable is the verifier?

We ran both tests on every buggy version and every reference fix, with three verifier setups, three times each. A perfect verifier fails the target test on all buggy versions and passes everything else. All three setups come within one point of that, with run-to-run standard deviation of at most 0.8 points. We use the cheapest, GPT-5.6 Luna in Codex.

04 · one bug, up close

A board that never arrives

Focalboard is an open-source project board, a bit like Trello. When you share a board with a teammate, it should show up in their sidebar. In the buggy version it never does. Nothing looks wrong to the person sharing, and the teammate can still open the board through a direct link. You only see the bug if you share the board, switch accounts, and look. It takes nine steps and two accounts. Step through it below; these are frames from our verifier’s own run.

    127.0.0.1:13200 · Focalboard

    Root causeAdding a member saves the membership but never files the board under the member’s default sidebar category. The fix is a single function call.

    Four agents saw it. Two called it a bug.

    Every agent got the same one-line request. We read the trajectories of four of them closely. All four reached the empty sidebar (the dashed column). What they did next differed. Click any card to read the agent’s own words.

    Claude Opus 5’s path is the instructive one. It saw the empty sidebar, read the unit tests, found that they expect no sidebar update, and concluded the behavior was intended. The existing tests had the bug baked in, and the agent trusted them over what a user would expect.

    05 · where it goes wrong

    Agents find the feature, then miss the bug

    To see where agents stop, we split each trajectory into five stages, each requiring the ones before it. GPT-5.6 Luna reads every trajectory and, using a description written from the reference fix, judges the first three. The behavior tests give the last two.

    1. 75.4%Find the feature. In AbanteCart, Grok 4.6 fixed phone numbers, addresses, and notifications on the profile page, but never tried the ID-photo upload where the bug was.
    2. 50.0%Identify the buggy behavior. The biggest drop. Agents often reach the feature but never run the interaction that exposes the bug. In Answer, Grok 4.6 accepted and reverted answers but never opened a question through its short-ID link. Or, as in Focalboard, they trigger the failure and don’t recognize it.
    3. 43.8%Diagnose the cause. In SearXNG, GLM 5.3 Flash saw escaped ampersands in search suggestions but blamed client-side encoding instead of server-side HTML escaping.
    4. 41.0%
      40.8%      Fix it, and keep everything else working. Once agents find the cause, they usually fix it, and rarely break anything along the way.

    Finding is the hard part

    To test this directly, we gave five agents a detailed prompt that describes the bug and the expected behavior, which is essentially a bug report. All five jump to 96.0–96.5%, and the gap between them nearly disappears. They can fix these bugs. They can’t yet find them.

    06 · what doesn’t help

    More time, more clicking

    Agents differ in work time by almost 10×, and it doesn’t track success. Grok 4.6 and GPT-6 Astra average about 13 minutes per task. Qwen 3.8 Flash and Kimi K3 take 102 and 90 minutes for similar or lower scores. On three tasks Qwen 3.8 Flash worked for nearly the full 8 hours without producing a patch. Giving the same agent a bigger budget helps from 20 to 40 minutes, then stops helping.

    Browser use looks the same. Agents spend 17–62% of their turns in the browser, and the share doesn’t predict the score: Qwen 3.8 Max takes 517 browser actions per task and passes 28%, while Claude Fable 5.1 uses the browser in a quarter of its turns and passes 56.5%. What matters is which scenarios an agent tries and whether it recognizes a failure when it sees one.

    Agents also don’t reach for the browser on their own. Our default prompt asks them to test like a real user. Without that line, GPT-5.6 Luna opened a browser on 2 of 200 tasks and GLM 5.3 on 6, and both scored lower. The harness matters less than the model: GPT-5.6 Luna ranges from 35.0% to 42.5% across five harnesses, best in its native Codex.

    08 · looking ahead

    Noticing is the general skill

    Most of what makes SWEeper-Bench hard has little to do with web apps. To pass, an agent has to step outside the code it is reading, picture how someone else will use the thing, try it, and notice when the result isn’t what that person would expect, even when the existing tests say everything is fine. It is the same habit that separates a careful engineer from a fast one, and it is what you would want from any agent that works without someone checking each step.

    It is also a habit we can measure, and possibly train. Our verifier judges only what a user would see, so it accepts any fix that works, and the same setup could reward agents for testing their own work. The target is clear: agents fix about 96% of these bugs once someone describes them, and catch at most 59% on their own.

    As agents build more software for individual people, software no QA team will ever look at, that gap is where users get stuck. We would like agents to do more than fix the bugs we report.

    Can they find them before we do?

    Limitations. SWEeper-Bench covers web apps only, and scores one known bug per task, so it measures recall rather than precision: fixes to other real issues earn no credit. Its behavior tests check function, not visual design, ease of use, or speed. Extending it to other interactive software is a natural next step.
