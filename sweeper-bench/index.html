Can agents discover bugs in interactive software?

1Princeton University  ·  *Equal contribution

Paper Code Data

TL;DR AI can build you an app in minutes. Finding the bugs in it is still your users’ job. SWEeper-Bench tests whether an agent can find and fix those bugs first. It has 200 real bugs from 200 open-source web apps, each hiding behind the right sequence of clicks. The agent gets no bug report, just a request like find and fix issues in board sharing. The best of 15 frontier agents gets 59%.

Who finds the bugs?

We used to ask AI for answers. Now we ask it for software: a sign-up form for the team trip, a booking page, a tiny tool for the office. A few minutes later it’s done, and it goes straight to the people who’ll use it.

And people are creative. Grandma opens it on an old iPad with the text cranked way up. Your cousin opens it from Tokyo. Two friends hit send at the exact same moment. This is interactive software with real users, and each of them finds a different way to break it.

Here’s the annoying part: you mostly can’t find these bugs by reading the code. The code looks fine. The tests pass. The bug only exists in a particular sequence of taps, on a particular device, or when two things happen at once. To find it, you have to actually use the app.

So today, users are the testers. They hit the bug, they complain, the complaint makes its way back to whoever built the thing, and everyone waits. Even the biggest companies work this way:

That loop was slow even when people built everything. Now AI builds apps on the fly, often for a handful of people and with no testing team in sight. Ideally, the agent that built the app would use it the way people will, find what’s broken, and fix it, before anyone else notices.

No benchmark measures this yet. SWE-bench and its successors hand the agent a bug report someone already wrote, so they test the fixing, not the finding. SWEeper-Bench starts before anyone has reported anything.

The best agent fixes 59%

Each task gives an agent the app’s code, the running app, a browser, and one vague sentence, like Find and fix issues in Focalboard’s board sharing and membership. That’s it. We tried 15 frontier agents. The best, Grok 4.6 in Cursor, fixed 59%. Nine of the fifteen fixed fewer than half. The bills vary wildly too: agents with similar scores differ in cost by more than 30×.

How it works

Every task is a real bug that was fixed in a real open-source web app, 200 apps in all. We rewind the app to just before the fix, so the bug is back, waiting for someone to tap through the app in just the right way. The agent never sees the bug report, the fix, or our tests.

To grade a fix, a second agent (the verifier) opens the repaired app in a browser and follows step-by-step tests: one checks that the bug is gone, the other that nothing nearby broke. It only judges what a user would see, so any fix that works counts.

How reliable is the verifier?

We ran both behavior tests on every buggy version and every reference fix, with three verifier setups, three times each. A perfect verifier fails the target test on the buggy version and passes everything else. All three setups come within one point of that, varying by at most 0.8 points between runs. We use the cheapest, GPT-5.6 Luna in Codex.

Test case example: shared team board doesn’t show up

Focalboard is an open-source project board, a bit like Trello. When you share a board with a teammate, it should show up in their sidebar. In the buggy version, it just… doesn’t. Nothing looks wrong from your side, so you only find out if you share the board, log in as your teammate, and look. Here’s our verifier doing exactly that:

    127.0.0.1:13200 · Focalboard

    The fix? One function call. Finding the bug is the hard part: four agents reached that empty sidebar, and only two thought it was a bug. Claude Opus 5 read the unit tests, saw that they expect no sidebar update, and decided the empty sidebar was intended. The tests had the bug baked in.

    Where agents fall short

    So where do agents lose it? We split each run into stages. About a quarter of the time, the agent never gets to the feature with the bug. Another quarter of the time it gets there and still misses the bug: it never triggers it, or it sees it and shrugs. Once it actually sees the bug, diagnosing and fixing it rarely go wrong.

    How easy is the fixing? Tell agents what the bug is, and every one we tried passes about 96%.

    More time doesn’t fix it

    Working longer doesn’t help much. Grok 4.6 spends about 12 minutes per task. Qwen 3.8 Flash spends 102, and scores a bit lower. Give the same agent a bigger budget and it improves up to about 40 minutes, then flattens out.

    Closing the loop

    Right now, the loop that makes interactive software work still runs through people: someone builds the app, users find what breaks, fixes follow. As AI builds more of what we use, it can close that loop itself: use the app like a person would, notice what’s off, fix it, and go again, until what reaches people just works. SWEeper-Bench measures how close agents are to doing that on their own.
